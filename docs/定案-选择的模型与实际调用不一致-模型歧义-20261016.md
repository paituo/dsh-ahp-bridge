# 定案：选择的自定义 DS4.1 与实际被调用的 Qwen3.8 不一致

> 日期：2026-10-16 22:xx
> 现象：UI 选 `DeepSeek-V41-Flash`（以为是自定义 DS4.1），右下角状态栏显示在用 `Qwen3.8-Flash-AI`，
> 模型回答自我报告"我用的是 deepseek-v4.1-flash"（**假话，它读的是提示词变量**）。

---

## 一、一句话结论

**这不是"模型没传过去"，而是"模型传过去但传错了 provider"** ——
桥的模型清单里 `deepseek-flash` 这个名字**同时属于两个官方 provider**
（`deepseek-official` 与 `deepseek-account`），而 VS Code 只能传**裸模型名**，
桥反查时**无条件取首项** ⇒ 落到 `deepseek-official` ⇒ 其 baseURL 硬编码
`https://api.deepseek.com/anthropic`，用 jxbw 网关的 key ⇒ **401** ⇒
`set_config_option` 失败 ⇒ 会话保持 pinned 默认 `Qwen3.8-Flash-AI`。

---

## 三、官方源码铁证（VS Code commit `6d62b1d5da`）

### 3.1 VS Code 侧的模型 id 编码（`codexModelSelection.ts`）

```ts
export function toCodexModelSelectionId(modelProvider: string, modelId: string): string {
    return `@provider=${encodeURIComponent(modelProvider)}:${encodeURIComponent(modelId)}`;
}
```

### 3.2 VS Code 编清单时**对所有模型套同一个 provider**（`codexAgent.ts:2296 + 2325`）

```ts
const modelProvider = configResponse.config.model_provider ?? CODEX_OPENAI_MODEL_PROVIDER;  // 全局单值
...
id: toCodexModelSelectionId(modelProvider, model.model),   // ← 用 model.model，不是 model.id！
name: model.displayName,
```

**关键三点**：
1. `modelProvider` 取自 `config/read`（桥的 M6 补丁固定给 `"openai"`）⇒ **无 provider 区分度**；
2. `id` 用的是 **`model.model`**（桥给的 `model` 字段），**不是** `model.id`；
3. 桥返回的 `provider` 扩展字段 **完全被无视**。

### 3.3 `thread/start` 只带拆开的两半

```ts
{ model: parsed.modelId, modelProvider: parsed.modelProvider }   // modelId 是裸名，provider 恒 "openai"
```

⇒ 桥拿到的只有 `"deepseek-flash"` + `"openai"`，**provider 信息已丢失**。

### 3.4 桥的猜首项（旧 `resolveDshModelValue`）

```js
const hit = translateModelSelectionToDsh(idRaw, "...", list);   // 内部 byName() = list.find(...) 取首项
// "deepseek-flash" → 命中 ["deepseek-official","deepseek-flash"]  ← 猜错！
```

### 3.5 为什么 `deepseek-official` 必 401（`dsh-llm-deepseek/lib/index.js`）

```js
const PUBLIC_BASE_URL = "https://api.deepseek.com/anthropic";
const baseURL = config.baseURL ?? environment?.get(BASE_URL_ENV)?.value ?? "https://api.deepseek.com/anthropic";
// 其 apiKeyEnv 默认引用 DEEPSEEK_API_KEY —— 而该 ref 存的是 jxbw 网关 key（只对 ai.jxbw.com 有效）
```

⇒ DSH `set()` → `resolveSelection` → `resolveCallConfig` 鉴权失败 ⇒ 抛 `AcpModelConfigError`
⇒ 桥 catch ⇒ `modelSyncError` ⇒ **会话保持 pinned 默认**（两个官方 provider 的 baseURL/凭据都不可用）。

### 3.6 模型为什么"自信地说错"

`dsh-agent/lib/types/model-selection.js` 的 `installModelSelection`：

```js
agentCtx.on('system-prompt/assemble', ...) → variables.provider = selected.provider; variables.model = selected.model;
agentCtx.on('agent/request', ...)          → provider: selected.provider, model: selected.model
```

**系统提示词里的 provider/model 变量来自 `selection`（用户意图），与实际 HTTP 路由解耦** ——
所以模型照着提示词回答"我用的是 deepseek-v4.1-flash"，**与真实调用无关**。

---

## 四、根因（单句）

> **模型清单里存在跨 provider 的同名项（`deepseek-flash`），而 VS Code 只能回传裸模型名，
> 桥无条件取首项 ⇒ 落到 URL/凭据均不可用的官方 provider ⇒ 设置失败并静默回落 pinned 默认。**

---

## 五、修复（E 盘，`bridge/src/translate.mjs`）

| # | 位置 | 改动 |
|---|---|---|
| 1 | `toCodexModels` | `model` 字段由**裸模型名**改为 **`<provider>/<模型名>`**（唯一定位）；重名条目 `displayName` 附 ` (provider)` 后缀 |
| 2 | `resolveDshModelValue` | 新增 ② **`provider/名` 精确反解**；新增 ③ **歧义预检**（裸名多条 ⇒ 返回 undefined，拒绝猜首项） |
| 3 | `translateModelSelectionToDsh` | 新增 ③-pre **`provider/名` 精确反解**，**优先于**既有的"末段名"解析（否则修了等于没修） |

### 为什么 `model` 字段可以改成 `provider/名`

- 官方只把它当**不透明字符串**参与 id 拼接（`@provider=openai:<model.model>`）与回传；
- `displayName` 独立存在，UI 展示不受影响；
- 对无歧义条目行为一致（`bumen/deepseek-v4.1-flash` 同样成立）。

### 附带补强：回读校验（不再乐观）

- `dsh-acp-client.setConfigOption`：新增 **P6 探针**（REQ 值 / RESP 回执 / 与请求值比对）；
- `bridge.mjs` thread/start + thread/settings/update：**以 DSH 回执的 configOptions 为准**判成功，
  日志明确打 `✅校验通过 / ❌校验不通过`，**彻底消灭"已落地"的乐观假象**。
